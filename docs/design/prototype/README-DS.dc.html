The design system, and what the prototype gets wrong

A complete review of the clickable app and the other prototypes: colour, section icons, type, buttons, badges, shape, depth and motion. For each, the rule to build, the SwiftUI to build it with, and every place where the prototype breaks the rule.

For Claude Code: this README and the board beside it win over the prototype. The prototype was built screen by screen over several weeks and drifted. When a screen disagrees with a rule here, build the rule. Every disagreement found is listed in “What to fix”, with where it is.
Applied to the current design, 23 November. Everything in “What to fix” is in the clickable app (with the Settings, Help and screenshot components it uses), the Welcome and menu bar prototype, the toolbar prototype and the Analytics prototype. All eight AI effects in section 7 play in the clickable app.
Fixed on 23 November, after the first pass: the Screenshots component’s styles applied to the whole app on any screen that shows a screenshot, and they loaded last. So on those screens footnotes stayed 10 pt and tertiary grey, chips kept their old size and radios were drawn at 14 pt. Settings did the same to the section icons while it was open. Both now only style their own boards (last row of “What to fix”).
Kept as they were, on purpose: pages Estados and Documentação e componentes, which hold boards 1–28, the component sheets and “Foundations”. They show the earlier design and are kept as history. Where they disagree with this README, this README wins.
Checked: all 71 scenes of the clickable app against the previous version: no text newly cut off and no script errors. The Settings, Welcome, toolbar, Help and screenshot boards were compared before and after. Every Accept and Send Reply was clicked.

Rule zero · one source of design truth (development rule, 23 November)

Design consistency is a rule of development, not a finishing step. Atlas must be easy to navigate because every screen speaks the same language: the same blue for “do it”, the same purple for “AI brought this”, the same type, the same buttons and the same motion. So:

  1. One module holds every decision: DesignSystem (Swift package in the app’s repo) with colour, type, spacing, radius, button, badge, pill, card and motion tokens, plus the five AI effects as view modifiers. Its values come from design-tokens.json, the same values as this README.
  2. No raw values in views. No hex colour, font size, corner radius, padding number, duration or spring in a screen’s code. Views use tokens: Color.ai, .atlasTextStyle(.headline), AtlasButtonStyle.rowAction, Motion.base, .aiArrived(). A value that doesn’t exist becomes a token first, here and in the module.
  3. The app shows its own design system. Debug builds have Debug → Design System Catalog… (⌥⌘D): a window drawn by the module itself with every colour (light, dark, high contrast), the type scale, the seven buttons, badges, pills and cards, and the five AI effects playing, each with Reduce Motion. It’s the first place to look when building or refining a screen, and the place to compare against.
  4. Before a screen is done: it uses only tokens; one filled blue per card or sheet; purple only on AI; motion only from the five effects; light, dark, high contrast and Reduce Motion checked in the catalog and the screen.
  5. Changing the system: change this README and board 64/68 first, then design-tokens.json and the module, then the screens. Never the other way round.

The files that start this (tokens JSON, the module skeleton, the catalog window and the rule for the repo’s CLAUDE.md) are in the handoff atlas-design-system.

State colours (added 23 November)

  • Blue for an action even near AI when no AI made it: “Use This Capture” (a capture you already have) is a tinted blue row action.
  • Accepted suggestions stay in place, neutral, with “Not pushed”; after the push they read the state Atlas reads back from Apple.
  • Failure is amber (warn tint), never purple, with what to do next. Loading data is a grey skeleton.
  • Starting AI from inside a page stays a secondary button with the sparkles glyph and purple label (Make Review Screenshots…, Try Again, Add StoreKit Configuration…, Scan the Code Again…).

How the review was done

  • Read every colour token, button class and icon colour in the six prototypes: the clickable app (Redesign), Settings, Welcome, Help, the toolbar prototype and Analytics.
  • Opened nine screens of the clickable app in light and dark and measured what the browser actually drew: every text size, every button height, every filled button.
  • Computed WCAG contrast for every text colour on its background, and the hue distance between the section colours.
  • All six prototypes share the same colour values, so the system already has one source; the toolbar and Analytics prototypes only lack the high-contrast set.

The idea in one paragraph

Atlas is a calm, native Mac tool with one extra voice: the assistant. So the interface has two colours that mean something and keeps everything else quiet. Blue is what you do (the one main action, selection, what you changed). Purple is what AI brings (suggestions, their counts, the assistant at work). Green, amber and red only describe state. The section colours exist to help people find places, never to mean anything. And motion belongs only to the assistant: when it works, arrives, writes or is accepted, something moves, gently and once; the rest of the app is still. That restraint is what makes the AI moments feel special.

5 · Badges, pills, sources

  • Badge = a count. Capsule 17 pt high, 11 pt semibold, tabular digits. Purple when it counts suggestions waiting for you, gray otherwise. Gone at zero. VoiceOver reads it in the label (“Store Page, 32 suggestions to review”).
  • Pill = a state. 20 pt, 11 pt semibold, tinted background with its own text colour: Live (ok), Not pushed (accent, with a dot), Suggested (ai, with edge), Needs an answer (warn), Rejected (err), and neutral states (gray).
  • Source chip = who made it: Claude Code, Built-in, AI provider, Claude Design. Neutral outline with a monogram; never coloured, so it doesn’t compete with the suggestion itself.

Rules

  • Only one looping effect on screen at a time, and only while work is actually running.
  • Nothing animates on page load or when switching sections. Motion means “something just happened”.
  • Purple light for AI; blue never animates.
  • Springs, not bounces: response about 0.35 s, damping about 0.8 for layout; 0.6 only for the count tick.
  • Every effect reads @Environment(\.accessibilityReduceMotion); translucency effects read accessibilityReduceTransparency.
  • Pair the end of real work with sound or haptics only when the window isn’t in front (a notification), never inside the window.

Rules (v2)

  • At most one loop on screen (the progress sweep), and only while work is really running.
  • No one-shot effect longer than 1.2 s. Nothing animates on opening a screen or switching sections.
  • Purple only for AI. Loading data that isn’t AI is a grey skeleton. Errors are amber. Blue never animates.
  • Every effect reads accessibilityReduceMotion; translucency reads accessibilityReduceTransparency.
  • The menu bar icon uses the same spark. With the window behind, the end of work is a notification; never a sound inside the window.

8 · Accessibility checklist

  • All readable text ≥ 4.5:1 (checked above); controls and focus rings ≥ 3:1.
  • Colour never alone: suggestions also have the “Suggested” pill and source chip; not pushed has the dot and the word.
  • Increase Contrast: the high-contrast accent and AI colours above; card lines go from 0.5 to 1 pt.
  • Full keyboard: Return is the primary button in sheets; ⌘K apps; ⌘, Settings; ⇧⌘P Review & Push.
  • VoiceOver: badges and pills are part of the element’s label; motion is never the only signal that work finished (the toast and the button label change too).

9 · Voice and content (23 November)

Atlas makes many decisions easy. Every word has to make the next decision faster. Short, clear, and enough to decide with full confidence.

Voice

  • Close and direct, like the Welcome screens: “Your key stays on this Mac.” Second person, active verbs, no hype, no exclamation marks.
  • Lead with the result, never the mechanism: “Lifetime: $79.99 → $59.99”, not “Claude Code analysed your pricing and suggests…”.
  • One idea per sentence, one number per sentence. Round numbers people read (“a third”, “2.4×”, “9 reviews”); exact numbers live in Details.
  • The first words earn the rest: put the reason the person cares first (“9 reviews call it too expensive.”).
  • Interface language: English, written to survive translation: no idioms, no wordplay, 30% room for German.

Words

  • Apple’s terms stay where people meet them in App Store Connect (Missing Metadata, Ready to Submit, Phased Release, Product Page, In-App Event), with one tooltip that says what they mean.
  • Atlas’s terms are one each: suggestion (not proposal, idea or recommendation), push (not upload, sync, publish), Review & Push, Autopilot, assistant, capture, set, template, price test (not experiment or A/B test; “Europe price test” in titles, Test a Price… on the button).
  • Plain words for Apple’s jargon in sentences: “Apple’s automatic prices” for equalized prices; “people who share analytics” for opt-in data.
  • Never: simply, just, easily, seamlessly, powerful, leverage, AI-powered, magic, please, oops, successfully.
  • Numbers and variables use ICU plurals and the person’s locale for numbers, dates and currency; prices show the country’s currency.

Text written by the assistant

Suggestions arriving through MCP must fill separate fields, and Atlas enforces the same limits: title (≤ 8 words), why (≤ 110 characters), details, evidence[], gloss (when not in the interface language) and confidence (1–3). Longer text is refused with the reason, so the assistant rewrites it. Built-in checks and Analytics findings are templates with variables that follow the same three layers.

10 · Information hierarchy on every screen (23 November)

  1. Top of every section answers three things, in order: what waits for you (summary line), what matters most (the first card), what happens if you accept (the one safety line of the screen).
  2. Order by impact: what blocks App Review → revenue → reach → polish. Inside a level, newest first.
  3. Budget per screen: one banner; one filled blue per card or sheet; details folded; at most 6 cards before “Show 9 More”.
  4. Group repeated decisions: “12 countries: lower price” or “5 languages: shorter subtitle”, with 3 examples visible and the rest one click away.
  5. Same card order everywhere: title · why · (gloss) · actions · details. Source chip and how-sure on the title line.
  6. Check the hard cases: 860 × 560 window, dark, Increase Contrast, larger text, German, Arabic.

The before/after of every text is in the spreadsheet Textos do Atlas (inventory, status per text and per action, the real app’s strings when Claude Code exports them).

11 · Sidebar footer and short windows (approved 24 November)

  1. Two rows, the same at every height: Settings and Help ▾ side by side, always with their names; below them the Version card with Submit…. Never icon-only.
  2. Help ▾ opens a menu: Atlas Help (⌘?), Show the Tour, Keyboard Shortcuts. The same items stay in macOS’s Help menu; Settings stays at ⌘, in the Atlas menu.
  3. Fixed footer: it sits on the sidebar’s glass and never scrolls. The section list scrolls under it only if it ever doesn’t fit, with a 14 pt fade at its bottom.
  4. When height runs short (rules on the sidebar’s own height, not the window’s): under 600 pt the app card drops its “5 other apps” line and group titles and rows tighten (rows 27 pt). At 560 pt every section stays visible without scrolling.
  5. SwiftUI: List with .safeAreaInset(edge: .bottom) for the footer; read the height with GeometryReader or onGeometryChange to switch the compact rules; the Help button is a Menu with .menuStyle(.button). Board 71 shows 780, 700, 600 and 560 pt.

12 · Language picker (approved 24 November)

  1. One picker, not tabs. Store Page and Screenshots use one pop-up button for the language; it changes the editor and the preview together. Tabs (English | Spanish | U.K.) don’t scale past a few languages and are replaced.
  2. The button says what’s waiting: the two-letter code, the full name (“English (U.S.)”, “Spanish (Spain)”), and under it “5 suggestions here” in purple. Beside it: ‹ › for the previous and next language (⌘[ and ⌘], shown in their help tags), Accept All Languages with the total, and “27 more in 5 other languages”.
  3. The menu is grouped: Suggestions to review first, each language with its purple count and New page where the App Store has no page yet; then Up to date with a check. Screenshots adds Uses English (U.S.) screenshots for languages that reuse the primary set. Accept All Languages… closes the menu.
  4. Find a language sits at the top of the menu with the total (“15 languages”), focused when the menu opens. Typing filters by name or code at once and keeps the groups; nothing found shows “No language matches”. Closing the menu clears it.
  5. SwiftUI: a Menu with a custom label, or a popover with a List and a .searchable-style field when there are more than 8 languages; sections for the groups; .keyboardShortcut("[") and ("]") on the arrows. Scenes sp-menu, sp-menu-find and sh-menu in Redesign; tiles in “Redesign · every state”.
